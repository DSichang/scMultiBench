    Run a method¶

    scMultiBench runs the original, unmodified method scripts from the reference repository - it never edits them. mtb.run reads a method's declaration from the registry, picks the right variant from the inputs you pass, builds the exact command line, runs it inside that method's own conda environment, and loads the typed output back into Python. (mtb.run_all does this for every method that fits a dataset folder, and scores the outputs - the category tutorials are built on it; this page is the single-method call underneath.)

    TL;DR

    import multibench as mtb

mtb.data.fetch("D28")                          # 137 MB reference dataset; no-op when present
res = mtb.run(
    "SCALEX", "diagonal",
    inputs=mtb.inputs_for("D28", "SCALEX", "diagonal"),   # {'rna': .../D28/rna.h5, 'atac_gas': .../D28/atac_gas.h5}
    out_dir="runs/scalex_d28",
)
res.output.shape   # -> (11014, 10)  joint embedding: 6,408 RNA + 4,606 ATAC cells x latent dims

    The run model¶

    Each method is declared once in the registry (multibench/engine/methods.yaml) as a MethodSpec. A spec lists the categories and tasks the method supports, the conda env it needs, and one variant per (category, modality-set) it can handle. A single mtb.run call walks this path:

    1. Look up the spec for method and collect the modality roles from your inputs (auxiliary roles like data_dir are ignored here).
    2. Select the variant whose when: matches (category, modalities). The match is exact on the set of modality roles - {"rna", "atac_gas"} selects the diagonal RNA + gene-activity variant, not the vertical one.
    3. Preflight the environment: with the default cmd_template, a missing conda env raises EnvironmentError naming the install command before anything is written.
    4. Convert inputs to the canonical scMultiBench .h5 (unless convert=False) into a per-run inputs/ folder.
    5. Build the command - [interpreter, entrypoint, *args, *params] - with the entrypoint resolved against the reference repo_path.
    6. Wrap and execute via cmd_template (default conda run -n <env> {cmd}) in the per-run out_dir working directory.
    7. Load the output by its declared kind (e.g. an embedding ndarray) into a RunResult.

    Each method needs its own conda environment

    The env each method needs is declared in the registry - for SCALEX it is scmb_torch (see mtb.method_info("SCALEX")["env"], the same name scan's env column, mtb.env.default_env_name and multibench env recipe / yml use) - and it must exist on your machine. Build it from the committed lockfile (or a prebuilt archive) with multibench env install --methods SCALEX --packed --run; multibench env doctor lists what exists and what is missing. mtb.run shells out with conda run -n <env> ...; if the env is missing the preflight raises EnvironmentError with that install command. multibench run ... --dry-run prints the exact command line without executing it (--param KEY=VALUE merges hyperparameters into it), the line an HPC job can carry.

    Inputs: roles and format flexibility¶

    inputs is a dict mapping each modality role to a file path (or an in-memory AnnData). Roles are the method's own argument names from the registry - for SCALEX's diagonal variant they are rna and atac_gas (gene-activity scores derived from ATAC). For a benchmark dataset, mtb.inputs_for(dataset, method, category) resolves them for you (and check=True verifies the files exist, are oriented features x cells and have one label per cell).

    You do not have to pre-convert your data. By default mtb.run routes every modality input through mtb.io.to_canonical, which adapts common formats to the canonical scMultiBench .h5 (HDF5 with matrix/data as features x cells, matrix/features, matrix/barcodes; sparse matrices are streamed, the file is gzip-compressed):

    Input you pass Handled by to_canonical
    .h5ad / .h5mu anndata / mudata readers (mod= picks the MuData modality)
    .csv / .tsv parsed to a matrix (cells x features)
    .loom anndata.read_loom
    in-memory AnnData used directly (layer= / obsm= select the matrix)
    already-canonical .h5 passed through unchanged 
    # both inputs become canonical .h5 before the method sees them; the D28
# files are already canonical, so to_canonical passes them through unchanged
mtb.run(
    "SCALEX", "diagonal",
    inputs={"rna": "data/D28/rna.h5", "atac_gas": "data/D28/atac_gas.h5"},
    out_dir="runs/scalex_d28",
)

    Pass convert=False when your inputs are already in the exact layout the method expects and you want scMultiBench to hand the paths through verbatim:

    mtb.run(..., convert=False)   # no format adaptation; paths used as-is

    Your own data as a dataset folder¶

    For run_all / scan (and for inputs_for) the inputs live in a dataset folder laid out by category - mtb.describe_layout(category) prints the contract. One call writes it from an AnnData or MuData:

    import anndata as ad
a = ad.read_h5ad("my_citeseq.h5ad")                 # X = RNA, obsm['protein'] = ADT, obs['celltype']
mtb.io.export_dataset(a, "data/MYCITE", rna="X", adt="obsm:protein", labels="obs:celltype")
#   -> data/MYCITE/rna.h5, adt.h5, cty.csv; batch="obs:sample" writes rna1.h5/cty1.csv ... per batch
mtb.io.from_mudata(mdata, "data/MYMULTIOME", rna="rna", atac="atac", atac_kind="peak",
                   labels="rna:celltype", category="vertical")   # -> rna.h5, atac.h5, cty.csv
mtb.scan("MYCITE", "vertical", data_path="data")    # files_ok / env_ok per method, with reasons

    Or file by file - to_canonical(src, "data/MYDIAG", modality="rna") picks the canonical filename for the modality, mtb.io.write_labels(labels, path) writes the single-column cty CSV, and read_canonical is the inverse (canonical .h5 -> AnnData, cells x genes). The modality argument is validated, and for ATAC it is the one place you say whether the matrix is peaks or gene activity - the two are not interchangeable, see the ATAC note printed by describe_layout. Pass category= with an ATAC matrix: category="vertical" writes plain atac.h5 whatever the representation, because the vertical (paired multiome) methods read the atac role and never open atac_peak.h5 / atac_gas.h5 (the representation is recorded nowhere on disk - feed the one method_info(m)["atac"] wants); diagonal / mosaic / cross keep atac_peak.h5 / atac_gas.h5. inputs_for / scan name a near-miss when they find the other file (atac.h5 not found; found atac_gas.h5 - vertical methods read atac.h5 ...), and scan's caveat column flags an ATAC role resolved to the wrong representation in either direction.

    Inspecting variants before you run¶

    Use mtb.method_info to see which categories, tasks, environment, and variant entrypoints a method declares - supports lists, per variant, the modality roles it expects and whether it needs labels.

    info = mtb.method_info("SCALEX")
info["env"], info["atac"], info["needs_labels"]   # ('scmb_torch', 'gene_activity', False)
info["supports"]
# [{'category': 'diagonal', 'modalities': ['rna', 'atac_gas'],
#   'output_kind': 'embedding', 'n_tunable': 0, 'needs_labels': False}]

    If the (category, modalities) you pass has no matching variant, mtb.run raises a KeyError that lists every (category, modality-set) the method does support, so the fix is usually to adjust your inputs keys.

    status tells you what is wired

    Every registry method has status: "verified": its command template was cross-checked against the real entrypoint and executed end to end on a reference dataset. mtb.method_info(m, verbose=True)["verification"] returns those runs (from the shipped multibench/files/final_verification.tsv) with their ARI, the baseline ARI from first verification and a verdict (DRIFT when a stochastic re-run leaves the tolerance). status says nothing about where the script lives: method_info(m)["availability"] is public for every method but SPIRAL and GPSA, whose scripts are benchmark-host-only (not published - scan reports them not runnable).

    Validated example: SCALEX diagonal integration on D28¶

    This is a real, GPU-validated run (2,233 s on our host - mtb.runtime_hint("SCALEX")). SCALEX performs diagonal integration (unpaired modalities bridged by shared features): an RNA population (rna) and an ATAC population summarised as gene-activity scores (atac_gas) from dataset D28, which mtb.data.fetch("D28") downloads (137 MB).

    run_scalex_d28.py
    import multibench as mtb

mtb.data.fetch("D28")
res = mtb.run(
    "SCALEX",
    category="diagonal",
    task="clustering",
    inputs=mtb.inputs_for("D28", "SCALEX", "diagonal", check=True),
    out_dir="/abs/path/runs/scalex_d28",
)

print(res.output.shape)   # -> (11014, 10)   joint embedding (RNA + ATAC cells x latent dims)
print(res.cmd)            # the exact argv that ran, including the conda wrapper

    Use absolute paths for inputs and out_dir

    The method script runs with out_dir as its working directory (step 6 above), and out_dir is also passed to the script as its save path. So a relative out_dir (or relative inputs) is resolved against the subprocess cwd, not your shell's cwd, which makes the outputs land in the wrong place. inputs_for returns absolute paths; pass an absolute out_dir too. No cmd_template is needed: the default conda run -n {env} {cmd} fills {env} from the spec (scmb_torch for SCALEX), so the run lands in the right conda env automatically.

    mtb.run returns a RunResult dataclass:

    Field Type What it holds
    method str the method id you ran
    out_dir Path the per-run working directory
    cmd list[str] the exact wrapped command line that executed
    output object the primary loaded output, here an embedding ndarray
    extra dict any additional declared outputs, keyed by filename
    stdout / stderr str captured subprocess streams 
    res.output            # numpy ndarray, shape (11014, 10), the joint embedding
res.extra             # {} for SCALEX (no extra outputs)
res.cmd[:3]           # [<conda>, 'run', '-n']  -> the cmd_template wrapper

    The embedding flows straight into evaluation and plotting. D28's labels are two files - one per modality, because the RNA and ATAC cells differ - and passing both as a list makes each cell's file of origin the batch for the batch metrics (see Evaluate a run):

    metrics = mtb.evaluate(res.output, category="diagonal", task="all",
                       labels=mtb.labels_for("D28"))   # {'rna_cty': ..., 'atac_cty': ...} - RNA cells first, then ATAC

    labels_for returns the files in the benchmark's cell-stacking order (RNA before ATAC; cty1, cty2, ... numerically), which is the order SCALEX stacks the cells, so the dict goes in directly; labels_for("D28", "SCALEX", "diagonal") follows that variant's own modality order. A dict you assembled in another order must pass label_order=[...] (or a list of paths in cell order). run_all finds that order for you and records it as summary.label_order.

    Choosing a cmd_template¶

    cmd_template decides how the built command is executed; {cmd} is the placeholder for the argv. The default targets the method's declared env:

    cmd_template = "conda run -n {env} {cmd}"   # default; {env} filled from the spec

    Override it to run elsewhere, e.g. an explicit env name, a Singularity container, or an HPC scheduler wrapper (the env preflight is skipped - you own the environment then):

    mtb.run(..., cmd_template="conda run -n scmb_torch {cmd}")

    mtb.run(..., cmd_template="singularity exec multibench.sif {cmd}")

    mtb.run(..., cmd_template="{cmd}")   # no wrapper, use the active interpreter

    repo_path points at the checkout of the reference scMultiBench method scripts; it defaults to config.DEFAULT.repo_path (auto-provisioned on first run). The variant entrypoint (e.g. tools_scripts/SCALEX/main_SCALEX.py) is resolved relative to it.

    Reading other output kinds¶

    The primary output is loaded by its declared kind. embedding / imputed / markers / graph outputs come back as numpy arrays; labels as a list of strings; coords as a path you handle yourself. Any additional files a variant declares land in res.extra, keyed by filename.

    Graph-output methods do not return an embedding

    A few methods emit a cell-graph rather than a coordinate embedding - notably scMoMaT, MIRA, and Seurat_WNN. For these, res.output is the graph representation, not a (cells x dims) embedding, and downstream steps that assume an embedding (e.g. ASW-style metrics) will not apply directly. mtb.method_info(method)["supports"] names each variant's output_kind; run_all scores scMoMaT through the UMAP it also writes (CHAIN_OK_GRAPH_METHOD) and reports Seurat_WNN as RUN_OK_NO_EMBEDDING.

    Spatial registration¶

    PASTE, PASTE2, SPIRAL and GPSA (task registration, category cross) align spatial slices; their output is aligned coordinates, not an embedding. PASTE and PASTE2 are public; SPIRAL and GPSA are availability="benchmark-host-only" - their scripts are not published, so a public install cannot fetch or run them (scan says benchmark-host-only: script not published, find_methods(task="registration", available=True) lists the two that run). They take a directory of slices instead of modality files - the role is data_dir, scan() shows their modalities as (data_dir), and you pass no modalities to run_all / inputs_for:

    <data_path>/MYVISIUM/            (or <data_path>/MYVISIUM/processed/)
    slice_0.h5ad  slice_1.h5ad  ...   one AnnData per slice, >= 2

    Each .h5ad needs .X (expression, spots x genes) and .obsm['spatial'] (spot coordinates, spots x 2). The upstream scripts glob data_dir + '*.h5ad' without sorting, so the slice index in the output follows glob order, not your numbering; SPIRAL also wants a unique leading token per filename (the part before the first _) - the package stages symlinks for that when needed. Output: aligned_slice_<i>.h5ad per slice, so run_all records RUN_OK_NO_EMBEDDING - clustering metrics do not apply, and registration metrics are not wired into mtb.evaluate in this version. scan() checks the directory for >= 2 .h5ad slices with obsm['spatial'] (the files_ok gate), and mtb.describe_layout("cross") prints this contract in full (describe_layout("spatial") points there - it is a task, not a category).

    res = mtb.run("PASTE", "cross", inputs={"data_dir": "/abs/path/data/MYVISIUM"},
              out_dir="/abs/path/runs/paste")
res.output            # path to the aligned slices
