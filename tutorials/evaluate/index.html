    Evaluate a run¶

    You have a run output - a joint embedding - and a set of cell-type labels. Now you want a number. mtb.evaluate takes that output and returns the scIB metrics that the scMultiBench paper reports, in a metric.csv-shaped frame you can read, save, or feed straight into a bubble plot.

    TL;DR

    import multibench as mtb

metrics = mtb.evaluate(
    result.output,                        # embedding: ndarray / DataFrame / AnnData / .h5 / .npy / .csv
    task="clustering",                    # ARI, NMI, ASW, iASW, iF1, cLISI
    labels=mtb.labels_for("D11")["cty"],  # one label per cell, in the embedding's row order
    # clustering= is optional - omitted, scIB's optimal-resolution Leiden
    # clustering is derived from the embedding
)
print(metrics)                            # index = metric, column "Value"

    What evaluate does¶

    mtb.evaluate(output, category=None, task="clustering", labels=None,
             clustering=None, batch=None, metric_set="scib",
             slow_metrics=False, only=None, *, obsm="X_emb", column=None,
             label_order=None, family=None, verbose=None) -> pd.DataFrame

    Cost. ARI, NMI and iF1 need scIB's optimal-resolution Leiden sweep (ten resolutions on a kNN graph of the embedding): tens of seconds for a few thousand cells, minutes for ~10^4. evaluate announces the sweep with one stderr line when it starts on more than 2,000 cells (verbose=None, the default; True / False force the line on or off); clustering= (your own assignment) or only= naming metrics that do not need it (ASW, iASW, cLISI, the batch family) skips it entirely.

    Under the hood it assembles a small AnnData carrying your embedding in obsm["X_emb"], with celltype, cluster, and batch as observation columns, builds a neighbour graph on the embedding, and runs the scIB metric functions over it. The result is a DataFrame indexed by metric name with a single "Value" column, the same shape as the metric.csv files the benchmark ships. The index uses the canonical metric spelling load_results uses (ARI, NMI, ASW, iASW, iF1, cLISI, ASW_batch, GC, iLISI, kBET), so a to_long frame concatenates with a stored table without duplicate metric columns - and it is never empty: a request that would select no metric raises instead of returning nothing.

    task Metrics computed
    "clustering" ARI, NMI, ASW, iASW, iF1, cLISI
    "batch" ASW_batch, GC (graph connectivity), iLISI (+ kBET with slow_metrics=True)
    "all" both groups above

    category (vertical, diagonal, mosaic, cross) is optional: it is validated when given (a typo raises ValueError listing the four), but the metrics do not depend on it. family= is accepted alongside task= - the same clustering / batch vocabulary load_results and recommend use (task="dimension_reduction" is served by the clustering group).

    Inputs¶

    evaluate is honest about what each metric group needs, and raises early if something is missing.

    labels is required; clustering is optional - clustering quality is measured by comparing predicted clusters against the ground-truth cell types, and the clusters are derived for you when you do not pass any.

    metrics = mtb.evaluate(
    result.output,
    task="clustering",
    labels="data/D11/cty.csv",   # single-column CSV, one header line, one label per cell
    # clustering="cluster.h5"    # optional: a precomputed clustering (h5 dataset
                                 # /obs/cluster_leiden, or any label-like input)
                                 # skips the internal Leiden sweep
)

    Batch correction is scored against a batch vector, so task="batch" (and task="all") additionally require batch - unless labels is a list (or an ordered dict) of two or more files, in which case each cell's file of origin (1, 2, ...) is the batch, the rule run_all applies (see below).

    metrics = mtb.evaluate(
    result.output,
    task="all",
    labels=mtb.labels_for("D52"),     # {cty1, cty2, cty3} in the benchmark's cell-stacking order
    # batch=my_batch_vector           # overrides the file-of-origin rule
)

    mtb.labels_for(ds) returns the files in the order the methods stack the cells (cty; cty1, cty2, ... numerically; rna_cty before atac_cty; labels_for(ds, method, category) follows that variant's own modality order), so the dict plugs in directly. A dict you built in any other order raises; pass label_order=["cty1", "cty2", "cty3"] - the keys in the method's stacking order, numbered files ascending and rna before atac, NOT alphabetical - or a list of paths in that order. Passing batch= under the default task="clustering" computes no batch metric and says so with a UserWarning (task="all" adds ASW_batch / GC / iLISI).

    Every input can be a path or an in-memory object:

    • output - a numpy.ndarray (cells x dims; a dims x cells array whose other axis matches the label count is transposed for you, with a warning), a pandas.DataFrame, an AnnData (.obsm[obsm], default "X_emb"), a scipy sparse matrix, or a path: .h5 (dataset data, the benchmark's embedding.h5), .h5ad, .npy, .csv / .tsv. A path that does not exist raises FileNotFoundError naming the path and the current working directory; an .h5 without a data dataset raises ValueError listing the keys it found (and says so when the file looks like a canonical input matrix - matrix/data - rather than an embedding).
    • labels / batch / clustering - a CSV path (header row; column x, the only column, or the last of two behind a barcode index - pass column= when the file is ambiguous), a list of CSV paths concatenated in that order, a dict as returned by mtb.labels_for (one entry, or several in the stacking order labels_for returns - otherwise label_order=), a 1-D array / Series / Categorical / list, a single-column DataFrame, or - when output is an AnnData (or a .h5ad path, read as one) - the name of an obs column, for clustering too. Values are compared as strings, so integer codes and names score identically.

    Row order: positional, or aligned by cell id

    Arrays, lists and files are matched positionally to the rows of output. A Series / DataFrame with a non-default index is aligned by cell id when output carries ids - an AnnData (obs_names) or a DataFrame with a non-default index: rows are reindexed to the output's order, and a missing or extra id raises ValueError naming the first offenders. Against a bare array there is nothing to align with, so the Series is matched positionally and a UserWarning says so - pass labels.to_numpy() to silence it, or an AnnData / DataFrame with ids to align. A Series with the default RangeIndex is positional and silent.

    Missing labels raises

    task="clustering" without labels raises ValueError; task="batch" / "all" without batch (and without a multi-file labels list) raises ValueError too, and a length mismatch says exactly what it saw (input length mismatch: emb has 2863 cells, celltype has 2864). These are programmer errors, not missing optional metrics - see graceful degradation below for the latter.

    Restricting what is computed¶

    only= names the metrics you want (a collection, not a bare string - that raises TypeError; an unknown name raises ValueError listing the vocabulary, mtb.plot.CLUSTERING_METRICS + mtb.plot.BATCH_METRICS). Everything else is skipped, including the Leiden sweep when no requested metric needs it - ARI and NMI compare the derived clustering against the labels (pass clustering= to score your own and skip the sweep) and iF1 scores every resolution of it, so those three run the sweep; ASW, iASW and cLISI do not:

    mtb.evaluate(result.output, labels=labels, only={"ASW"})               # no Leiden sweep, ~seconds
mtb.evaluate(result.output, labels=labels, clustering=my_clusters,
             only={"ARI", "NMI"})                                      # your clustering, no sweep
mtb.evaluate(result.output, task="all", labels=labels, batch=batch,
             only=["ARI", "ASW_batch", "GC"])

    only= is validated against the task: a batch metric (ASW_batch, GC, iLISI, kBET) needs task="all" or "batch" plus batch= (or a multi-file labels) - under task="clustering" it raises ValueError: GC is a batch metric: pass task="all" (or "batch") and batch=<vector> instead of returning an empty frame; a clustering metric under task="batch" raises likewise; kBET needs slow_metrics=True. slow_metrics=True adds kBET (shells out to R; hours on large datasets).

    Are my numbers comparable?¶

    The metrics in the shipped tables and the metrics evaluate returns are computed the same way, so yes - provided you feed the same things:

    • labels - the dataset's cty CSV(s), one label per cell in the embedding's cell order. mtb.labels_for(ds) returns them ({"cty": ...} for single-label datasets, {"rna_cty", "atac_cty"} for diagonal, {"cty1", "cty2", ...} per batch) in the benchmark's cell-stacking order, so labels=mtb.labels_for(ds) is the whole recipe for a multi-file dataset; a dict in any other order needs label_order=.
    • clustering - omitted, scIB's optimal-resolution Leiden: ten resolutions from 0.2 to 2.0 on the embedding's neighbour graph, keeping the one with the highest NMI against the labels. Pass clustering= to score your own.
    • metrics - the scib.metrics functions; iASW / iF1 score every label (the isolated-label threshold is set to the batch count + 1, so no label is excluded).
    • cLISI / iLISI - need scib's compiled LISI helper (knn_graph.o). The shipped binary is Linux x86-64; when it cannot run (macOS, another architecture) evaluate rebuilds it in place once, with scib's own build line, if g++ / c++ / clang++ is on PATH, and only otherwise records NaN with a warning that carries the exact g++ command (see Installation).

    Batch vector on multi-batch layouts¶

    run_all scores batch metrics against the label file each cell came from: cty1.csv -> 1, cty2.csv -> 2 (cross / mosaic), rna_cty.csv -> 1, atac_cty.csv -> 2 (diagonal) - the winning permutation is recorded in summary.label_order, and summary.batch_source says file_of_origin. Batches within one file (donors inside rna.h5, say) are therefore not represented. When your dataset has them, re-score with the vector it really has - nothing is re-run:

    res = mtb.run_all("MYDATA", "cross", out_dir="out/", batch=my_batch_vector)   # at run time, or
res2 = res.rescore(batch=my_batch_vector)          # on the stored outputs; batch_source becomes 'user'
mtb.evaluate(Path(res.results[0]["out_dir"]) / "embedding.h5",               # one stored output
             task="batch", labels=labels, batch=my_batch_vector)

    Re-runs are stochastic¶

    Most methods are non-deterministic, so a re-run does not reproduce the stored decimals. The package ships every verification run (multibench/files/final_verification.tsv; read it per method with mtb.method_info(m, verbose=True)["verification"] - a list of {dataset, category, status, wall_s, ARI, baseline, verdict, note}, where baseline is the ARI recorded when the method was first verified and verdict is DRIFT when the re-run leaves the tolerance): on D11, 11 of 13 methods re-scored within ~0.02 ARI of their baseline, while VIMCCA moved 0.599 -> 0.695 and Concerto 0.408 -> 0.498. Compare ranks, not decimals, and prefer aggregate="summary" over several datasets when ordering methods.

    Graceful degradation¶

    A few scIB metrics depend on external machinery that is not always present. Rather than failing the whole evaluation when one optional metric cannot run, evaluate computes each metric defensively: if it raises, the metric is recorded as NaN with a warning, and every other metric still returns.

    Metric Needs If unavailable
    cLISI, iLISI scib's compiled LISI helper rebuilt in place when a C++ compiler is on PATH; else NaN + warning (with the rebuild command)
    kBET R via rpy2, and slow_metrics=True NaN + warning

    So on a machine without the LISI binary and without a compiler, a task="clustering" call still gives you real ARI, NMI, ASW, iASW, and iF1, only cLISI comes back NaN.

    Reading the result¶

    >>> metrics
       Value
ARI    0.812
NMI    0.847
ASW    0.591
iASW   0.604
iF1    0.733
cLISI    NaN     # LISI binary not runnable here and no compiler to rebuild it

    It is a plain DataFrame, so you can save it as the benchmark's metric.csv directly:

    metrics.to_csv("metric.csv")

    Closing the loop: tidy -> bubble plot¶

    The wide "Value" frame is the right shape for one run. To compare across methods and datasets, and to draw the scIB-style bubble table from the paper, reshape it to the long frame that plot.bubble and load_results use, with mtb.to_long:

    mtb.to_long(value_df, method, dataset, category, *,
            clustering="default", source="user", needs_labels=None) -> pd.DataFrame
# columns: metric, value, method, dataset, category, clustering, source

    to_long emits the same seven columns load_results returns - source is "user" unless you say otherwise, so your rows stay distinguishable after a concat - and maps each metric name to its canonical form (raising if two rows collapse onto the same name, so nothing is double-counted); evaluate already emits the canonical spelling, so the result lines up with mtb.load_results and can be concatenated with the stored tables without duplicate metric columns. needs_labels=True adds a needs_labels column that gives your (supervised) method the bubble table's L badge. It accepts evaluate's frame, a Series, or the CSV read back with a metric column; a frame that is already long, or one without a Value column, is rejected with a message naming the shape (and the df.T.set_axis(["Value"], axis=1) fix for a one-row frame).

    import pandas as pd
import multibench as mtb

mine = mtb.to_long(metrics, method="SCALEX", dataset="D28", category="diagonal")
bench = mtb.load_results("diagonal", dataset="D28", source="rerun")   # the package's re-run sweep

fig = mtb.plot.bubble(
    pd.concat([bench, mine]),
    metrics=["ARI", "NMI", "ASW", "GC"],   # this column order, left to right
    title="Diagonal integration, D28 + SCALEX",
    save="bubble.pdf",
)

    plot.bubble returns a Matplotlib Figure (circle radius tracks rank, fill tracks value, one Overall bar per metric family). See the plotting tutorial for the full set of options, including published vs re-run tables.

    metric_set="scib" is the only metric set

    Any other metric_set raises ValueError listing the one that exists; task="registration" raises NotImplementedError (its metrics are not wired into evaluate - see Spatial registration), and any other task token raises ValueError naming the vocabulary.
